# Contributing to kaltura-knowledge

Thank you for sharing what you've learned. Small, clearly labeled notes are more useful than polished ones, so don't wait until you're certain.

The core idea: **a note can be tentative, as long as it says so.** We label how well something is established instead of trying to rule on truth.

## Ways to contribute

- **Add a note** for something you learned or observed (see below).
- **Improve an existing note:** add detail, test it in your environment, or mark it disputed or outdated.
- **Ask or discuss** in [Discussions](../../discussions) when you're unsure, or want to find out whether others have seen the same thing.

## Adding a note

1. Copy [`templates/knowledge-note.md`](templates/knowledge-note.md) into the best-fit folder under [`notes/`](notes) (for example `notes/api/`). If none fits, pick the closest and say so in your PR.
2. Name the file in lowercase with hyphens, describing the topic: `entry-flavor-deletion-behavior.md`.
3. Fill in the front matter and every section. If a section doesn't apply, write "Not applicable" rather than deleting it.
4. Open a pull request. Direct pushes to `main` are blocked.

### Front matter fields

| Field | What to write |
|---|---|
| `status` | `Unverified`, `Confirmed`, `Disputed`, or `Outdated`. New notes are almost always `Unverified`. |
| `source` | Where this came from: your own testing, a support ticket, or a documentation URL. |
| `environment` | Product (KMC, KAF, MediaSpace, REACH, API), version if known, and relevant configuration. This is what makes a note reusable or not. |
| `last_reviewed` | Date (YYYY-MM-DD) a person last checked it, or "Not yet reviewed". |
| `ai_assisted` | `Yes` or `No`. See [AI-generated content](#ai-generated-content). |

### Choosing a status

- Use **Unverified** if you saw it once or heard it from someone.
- Use **Confirmed** only if the Verification section says how: you reproduced it, Kaltura documentation states it (link it), or Kaltura support confirmed it (reference the case, without private details).
- Moving a note to **Confirmed** needs a reviewer other than the author.

### Writing tentative information well

- Say what you actually observed: "In our MediaSpace, deleting a flavor returned success but the entry still played" rather than "Kaltura doesn't delete flavors".
- Separate what you saw from what you assume is the cause.
- Note what you did *not* test.

## What not to include

- Passwords, API secrets, admin secrets, session tokens (KS), or `.env` contents
- Partner IDs, internal URLs, or hostnames that identify your institution's setup
- Personal information about students, staff, or vendors, including names from meeting discussions
- Content copied from private support portals, vendor documentation behind a login, or other material you can't share. Link to public sources instead.

Remember that git keeps history, so a mistake isn't fixed by deleting it in a later commit. If something sensitive is committed, tell a maintainer immediately.

## AI-generated content

Many of us will use AI assistants to draft notes, and that's welcome. The rules:

- Set `ai_assisted: "Yes"` if an AI wrote or substantially shaped the note.
- **A human must read it and stand behind it** before opening the PR. AI tools can state invented API parameters, behaviors, and version numbers with total confidence.
- Don't mark AI-written content **Confirmed**. Confirmation comes from testing or an authoritative source, not from the AI.
- Don't include real credentials or identifying details in prompts or output.
- Meeting summaries generated by Zoom or another tool don't belong in this repository (see [Meeting material](#meeting-material)).

If you use an AI coding assistant, it should read [AGENTS.md](AGENTS.md).

## Reviewing contributions

Maintainers and reviewers should check:

1. **Labeled honestly.** Does the status match the evidence in Verification and Source?
2. **Clear scope.** Does the environment field say when this applies?
3. **Nothing sensitive.** See the list above, including in examples and screenshots.
4. **Complete.** All template sections are present.
5. **Sources.** Claims of "documented" or "confirmed by support" have a reference.

Guidelines:

- `Unverified` notes can be merged after a quick check. We want them in, as long as they're labeled.
- Moving a note to `Confirmed` needs a second person, not the author, and updates `last_reviewed`.
- If a reviewer disagrees on the facts, don't block the note: merge it as `Disputed` or ask the author to reword what was observed, and continue the conversation in Discussions.
- Prefer suggestions and questions to rejections. The goal is a welcoming place to write things down.

## Meeting material

Please don't add meeting summaries, transcripts, or recordings to this repository, and don't cite a meeting as a note's `source`. Community meetings are candid, often about people's own environments or the vendor, and this repository is public.

Raw meeting material is better kept in a private, access-controlled space, with only redacted, distilled findings published here as structured notes. How that should work is still to be agreed with the community.

In the meantime, if you learned something in a meeting that you've also seen or tested yourself, write it up as a normal note with your own testing as the source.
